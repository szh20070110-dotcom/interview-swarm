### T01 · 为一个「文档检索」功能设计 HTTP 接口 〔自研〕

**题目**：请设计 `POST /api/v1/knowledge/search` 的接口契约，说明入参、出参、错误码、鉴权、分页与超时处理。若同一请求被客户端重复提交，你怎么保证幂等？

**考察目的**：校招后端最基础也最容易被忽略的接口设计能力，验证是否具备契约意识与边界意识。

**参考答案要点**
1. 入参：`kb_id`、`query`、`top_k`、`filters`、`page/page_size`；出参：`items[]`（chunk_id、score、snippet、source）、`total`、`trace_id`。
2. 鉴权：网关注入租户与用户身份，服务内做 `kb_id` 归属校验，禁止越权检索。
3. 错误码分层：400 参数、401/403 鉴权、404 资源不存在、429 限流、500 内部错误、503 依赖不可用。
4. 超时与重试：检索链路设总预算（如 800 ms），对向量库调用设短超时；读请求可重试，写请求不盲目重试。
5. 幂等：查询天然幂等；若带写副作用（记录检索日志/计费），用 `request_id` 去重表或 Redis SETNX。

**评分锚点**
- **5**：契约完整，主动说明越权校验、超时预算、`trace_id`、幂等键与去重存储，能举出一次真实接口踩坑。
- **4**：字段与错误码齐全，能说清鉴权和超时，幂等只提到查询天然幂等。
- **3**：能写出基本入参出参与 200/400/500，鉴权与幂等需提示。
- **2**：只会写 URL 和返回 JSON，缺错误码、分页、鉴权。
- **1**：无法给出接口结构，或把 GET 用于带敏感参数的查询并说不清原因。

### T02 · 联合索引与慢查询 〔自研〕

**题目**：`orders` 表有 `tenant_id`、`status`、`created_at`、`customer_id` 四个常用条件。请给出索引方案，并解释为什么「最左前缀」重要。什么情况下索引会失效？

**考察目的**：验证数据库基本功，是否能从执行计划而非「加索引就好」的层面思考。

**参考答案要点**
1. 典型方案：`(tenant_id, status, created_at)` 覆盖「租户 + 状态 + 时间排序」；按客户查询另建 `(tenant_id, customer_id, created_at)`。
2. 最左前缀：B+ 树按索引列顺序排序，跳过前导列无法有序定位；范围条件后的列通常无法继续用于精确匹配。
3. 失效场景：函数/表达式包裹列、隐式类型转换、前导模糊 `LIKE '%x'`、`OR` 混用未覆盖列、选择性过低、统计信息过期。
4. 验证方式：`EXPLAIN` 看 `type`、`key`、`rows`、`Extra`（是否 filesort/临时表）。
5. 取舍：索引增加写放大与存储，需按读写比和选择性权衡，避免堆叠冗余索引。

**评分锚点**
- **5**：给出两套索引并说明顺序依据，能讲最左前缀原理与至少 4 种失效场景，提到 `EXPLAIN` 与写放大。
- **4**：索引方案合理，能讲最左前缀与常见失效，缺执行计划或取舍。
- **3**：知道加联合索引、知道最左前缀，失效场景说不全。
- **2**：只会说「给常用字段加索引」，无法解释顺序。
- **1**：认为索引越多越好，或不懂索引结构。

### T03 · 事务与并发扣减 〔自研〕

**题目**：库存扣减场景，两个请求同时下单。请说明你会怎么保证不超卖，并比较悲观锁、乐观锁、Redis 预扣减三种方案的取舍。

**考察目的**：验证事务、隔离级别与并发控制的理解，是否能落到业务约束。

**参考答案要点**
1. 单库方案：`UPDATE stock SET qty = qty - ? WHERE id = ? AND qty >= ?`，用影响行数判断，依赖行锁与原子更新。
2. 悲观锁：`SELECT ... FOR UPDATE`，一致性强但持锁时间长、易阻塞；需固定加锁顺序避免死锁。
3. 乐观锁：版本号/CAS，失败重试；适合冲突低的场景，高冲突时重试成本高。
4. Redis 预扣减：Lua 脚本保证原子性，抗高并发；需考虑缓存与 DB 一致性、扣减后失败回补、宕机丢数据。
5. 兜底：唯一约束/流水表、对账补偿、消息队列削峰；说明隔离级别（RR 下快照读与当前读的差异）。

**评分锚点**
- **5**：三种方案都能讲清适用边界与失败补偿，提到死锁、重试、对账，能给出组合方案。
- **4**：能写原子 UPDATE 与乐观锁，比较两种方案，Redis 方案只提概念。
- **3**：知道加锁或版本号，能说基本思路，隔离级别不清。
- **2**：只会「加 synchronized」，不懂分布式场景下无效。
- **1**：无法说明如何避免超卖。

### T04 · RAG 的完整链路与后端职责 〔知识库·转译〕

**题目**（源：`KB-A` AI Agent 工程师 Q2）：请完整讲一遍 RAG 的工作流程。作为后端工程师，你认为哪些环节最容易出问题？你会怎么兜底？

**考察目的**：公司核心业务是私有知识库，此题验证候选人是否理解主链路，以及能否识别工程风险点。

**参考答案要点**
1. 链路：文档接入 → 格式解析/OCR → 清洗去重 → 语义切片 → 向量化 → 入向量库 → 查询向量化 → 相似度召回（可加重排）→ Prompt 拼接 → 大模型生成 → 答案与溯源输出。
2. 后端高风险点：大文件解析超时与重试、切片任务积压、向量库写入失败、召回为空、模型超时/限流、上下文超长、并发写入版本冲突。
3. 兜底：任务队列 + 幂等键 + 失败重试与死信；解析结果落库可重放；检索空结果返回「未找到」而非硬编；模型调用设超时、降级与熔断；答案带 `source` 溯源。
4. 可观测：记录 `doc_id`、`chunk_id`、召回分数、耗时、模型版本，便于定位「答不准」。
5. 权限：检索前按租户/角色过滤，避免越权召回。

**评分锚点**
- **5**：链路完整无缺环，能指出 4 个以上工程风险并给出队列/幂等/熔断/溯源等具体兜底，主动提权限过滤。
- **4**：链路完整，能指出 2–3 个风险并有基本兜底，缺可观测或权限。
- **3**：能说出「解析、切片、向量、检索、生成」主干，风险点泛泛。
- **2**：只知道「向量库 + 大模型」，链路顺序混乱。
- **1**：把 RAG 等同于「把文档丢给大模型」。

### T05 · 向量检索：召回不准怎么排查 〔知识库·转译〕

**题目**（源：`KB-A` AI 算法工程师 Q5，转译为后端视角）：知识库问答经常「答非所问」。从检索链路看，你会按什么顺序排查？切片的粒度、相似度阈值、Top-K 分别怎么调？

**考察目的**：验证候选人是否具备「按链路分层定位」的工程思维，而不是一句「模型不行」。

**参考答案要点**
1. 排查顺序：数据层（文档是否解析乱码/缺页/重复）→ 切片层（是否断章取义、块过大/过小）→ 向量层（模型是否匹配、维度/归一化是否正确）→ 召回层（Top-K、阈值、是否需 rerank）→ 生成层（Prompt 是否约束、上下文是否截断）。
2. 切片：按语义/标题层级切，保留重叠窗口；块过大导致噪声，过小导致语义不完整；用真实问题集回归。
3. 阈值：过低引入噪声，过高导致召回为空；应基于标注问题集看 Precision/Recall 曲线选点。
4. Top-K：先大召回再 rerank，或按场景分层；K 增大提升召回但增加延迟与噪声。
5. 度量：建立 50–200 条「问题-正确文档」评测集，离线评估命中率，线上看点赞/追问/转人工率。

**评分锚点**
- **5**：排查顺序清晰，能讲切片重叠、阈值与 K 的 trade-off，提出 rerank 与评测集，给出量化指标。
- **4**：能分层排查，讲清切片与 Top-K，评测只提「拿问题试」。
- **3**：知道切片和相似度，排查停留在「换个模型」。
- **2**：只能说出「向量库搜得不准」，无方法。
- **1**：不理解召回与生成的区别。

### T06 · 非结构化文档入库流水线 〔知识库·转译〕

**题目**（源：`KB-A` AI Agent 工程师 Q3）：一批 PDF、Word、扫描图片要进入私有知识库。请设计后端入库流水线：任务如何拆分、状态如何管理、失败如何重试、如何避免重复入库？

**考察目的**：贴近公司私有知识库交付场景，考察任务编排与数据一致性。

**参考答案要点**
1. 状态机：`UPLOADED → PARSING → CLEANING → CHUNKING → EMBEDDING → INDEXED`，另有 `FAILED/RETRYING/DELETED`。
2. 任务拆分：上传后只落原始文件与元数据，解析/切片/向量化各自异步，按文档或分片粒度投递队列。
3. 幂等：以 `doc_id + file_hash + chunk_index + pipeline_version` 做唯一键，重复任务直接跳过或覆盖。
4. 重试：区分可重试（超时、限流）与不可重试（文件损坏、格式不支持）；指数退避 + 最大次数 + 死信队列 + 人工介入。
5. 一致性：先写新版本再切流量，旧版本延迟删除；向量库与元数据库双写要有补偿/对账任务。
6. 可观测：每阶段耗时、失败率、积压量；大文件限流与并发控制。

**评分锚点**
- **5**：给出完整状态机与幂等键，区分可重试错误，设计死信与对账，提到版本切换。
- **4**：状态与队列设计合理，有重试和去重，缺对账或版本切换。
- **3**：知道异步处理与重试，状态管理粗糙。
- **2**：同步串行处理，失败即丢，无幂等。
- **1**：没有流水线概念，只会「上传后调接口」。

### T07 · Agent 工具调用网关设计 〔知识库·转译〕

**题目**（源：`KB-A` AI Agent 工程师 Q4）：Agent 需要调用「查工单」「查库存」「发通知」三个内部接口。请你设计一个工具调用网关：如何描述工具、如何校验参数、如何处理超时与失败、如何防止 Agent 乱调？

**考察目的**：验证对函数调用、外部依赖治理与安全边界的理解。

**参考答案要点**
1. 工具注册：名称、描述、JSON Schema 参数、权限范围、超时、幂等标识；描述要能让模型正确选择工具。
2. 参数校验：服务端二次校验（类型/范围/枚举），不信任模型输出；高风险参数做白名单。

- **5**：工具描述与 Schema 完整，服务端二次校验，权限+审计+预算控制齐全，能讲清哪些工具可重试。

### T10 · Redis 缓存三大问题 〔自研〕

**题目**：知识库详情接口要加缓存。请说明缓存穿透、击穿、雪崩的区别与应对，并说明缓存与数据库不一致时你如何取舍。

**考察目的**：验证缓存使用的边界意识，避免「加 Redis 就快」的初级思维。

**参考答案要点**
1. 穿透：查不存在的数据 → 空值缓存（短 TTL）、布隆过滤器、参数校验。
2. 击穿：热点 key 过期 → 互斥锁/逻辑过期/单飞（singleflight）。
3. 雪崩：大量 key 同时过期或 Redis 宕机 → 过期时间加随机、多级缓存、熔断降级、集群高可用。
4. 一致性：Cache Aside 先更新库再删缓存；延迟双删；订阅 binlog 异步失效；接受短时间不一致并设 TTL 兜底。
5. 取舍：强一致场景不加缓存或用短 TTL + 版本号；读多写少才适合缓存。

**评分锚点**
- **5**：三个问题定义与方案准确，能讲逻辑过期/单飞，一致性能说清延迟双删与业务取舍。
- **4**：三个问题能区分并有方案，一致性只提「先更库再删缓存」。
- **3**：知道穿透加空值、雪崩加随机过期，击穿说不清。
- **2**：混淆三个概念。
- **1**：只会在代码里 `get/set`，无失效策略。

### T11 · 接口 P99 从 800 ms 降到 200 ms 〔自研〕

2. 归因：抽样 badcase 分类（解析、切片、召回、排序、生成、权限），算占比。
3. 措施：按占比排序做数据清洗、切片优化、混合检索 + rerank、Prompt 约束、阈值与拒答。
4. 验证：离线评测集 + 小流量 A/B，看核心指标与延迟、成本。
5. 迭代：灰度放量、监控、badcase 回流；设止损线。

**评分锚点**
- **5**：指标口径、评测集、badcase 归因、措施排序、A/B 与回流闭环完整，考虑延迟成本。
- **4**：有指标与措施，验证只做离线。
- **3**：知道清洗数据和换模型，缺指标与验证。
- **2**：目标无法拆解，只会「优化算法」。
- **1**：无数据驱动意识。

## 三、行为类（B01–B07｜HR 面官主问）

### B01 · 多任务冲突与优先级 〔知识库〕

**题目**（源：`KB-H` 题目 2）：同时有线上故障、导师安排的需求、你自己的学习任务，你怎么排优先级？请举一个真实例子。

**考察目的**：考察责任心、统筹与闭环，适配项目制忙闲交替的节奏。

**参考答案要点**
1. 判断标准：影响面 × 紧急度 × 不可逆性；线上故障优先止血。
2. 动作：立即同步相关人、给出预计时间、必要时求助或升级，不闷头干。
3. 取舍：明确告知被推迟方，给出新时间点，形成闭环。
4. 例子：有具体情境、自己的动作、结果与复盘。
5. 边界：不长期靠加班掩盖规划问题。

**评分锚点**
- **5**：有清晰判断框架，例子真实，主动同步与闭环，能反思规划问题。
- **4**：优先级合理，例子完整，同步意识一般。
- **3**：知道先做重要的，例子空泛。
- **2**：被动等待安排，或多头都答应却完不成。
- **1**：无优先级概念，情绪化处理。

---

### B02 · 压力与客户质疑 〔知识库〕

**题目**（源：`KB-H` 题目 2）：客户在现场质疑「你们系统就是不好用」，情绪比较激动。你作为后端支持，会怎么处理？你如何调节自己的压力？

**考察目的**：考察情绪管理、客户意识与问题解决，政企交付高频场景。

**参考答案要点**
1. 先接情绪：倾听、复述确认、不争辩；把「好不好用」转成可验证的问题。
2. 再定事实：复现步骤、影响范围、日志证据；区分缺陷、配置、使用习惯。
3. 给方案：临时绕过 + 修复计划 + 时间点；超出权限及时升级。
4. 压力调节：运动/拆分任务/求助/复盘，不把情绪带给同事与家人。
5. 边界：不承诺做不到的事，不贬低客户或同事。

**评分锚点**
- **5**：先情绪后事实再方案，有真实案例，压力调节方式健康，边界清晰。
- **4**：处理顺序正确，有案例，调节方式一般。
- **3**：知道安抚和解释，缺可执行方案。
- **2**：容易对抗或过度承诺。
- **1**：情绪化、推责或无法承压。

---

### B03 · 团队冲突 〔自研〕

**题目**：你和同学/同事在技术方案上意见相反，对方资历比你高。你怎么表达不同意见？如果最后采用了对方的方案但失败了，你会怎么做？

**考察目的**：考察沟通方式、原则性与团队意识。

**参考答案要点**
1. 表达：基于事实与数据，先对齐目标，再讲方案 trade-off；对事不对人。
2. 倾听：确认对方约束与信息优势，必要时承认自己遗漏。
3. 决策：尊重决策机制；保留意见可记录，但执行到位。
4. 失败：不事后嘲讽，先补位解决，再复盘方案假设哪里错了。
5. 反思：自己当初是否表达不清、证据不足。

**评分锚点**
- **5**：有事实依据的沟通方式，尊重决策且执行到位，失败后先补位再复盘。
- **4**：能理性表达，失败后态度正面。
- **3**：知道沟通，但容易回避冲突。
- **2**：要么硬顶要么完全沉默。
- **1**：人身攻击或推责。

---

### B04 · 一次失败与复盘 〔自研〕

**题目**：讲一次你失败的经历（比赛、项目、考试均可）。你当时怎么归因？后来做了什么改变？现在回看，归因还成立吗？

**考察目的**：考察自我认知、归因方式与成长性，校招重点看可塑性。

**参考答案要点**
1. 事实：情境、目标、自己的选择、结果，不甩锅。
2. 归因：区分能力、努力、策略、外部因素；重点落在可控项。
3. 行动：具体改变（流程、习惯、学习方法），有后续结果。
4. 反思：现在回看是否有更深层原因，是否修正过判断。
5. 诚实：不把失败包装成「其实我成功了」。

**评分锚点**
- **5**：事实清楚、归因可控、行动具体且有后续验证，能二次反思。
- **4**：能诚实复盘，有改进行动，深度一般。
- **3**：承认失败，归因偏外部或行动笼统。
- **2**：把失败说成运气/他人问题。
- **1**：拒绝承认或无法举例。

---

### B05 · 主动补位与责任心 〔自研〕

**题目**：团队里有一块没人认领的脏活（比如补文档、修历史数据），不影响你的 KPI。你会怎么做？请举一个你主动补位的例子。

**考察目的**：考察责任边界与团队意识，避免「只做分内事」。

**参考答案要点**
1. 判断：是否影响交付/他人、是否有人更合适、自己的时间成本。
2. 行动：主动认领或部分认领，约定范围与时间，不抢功不抱怨。
3. 例子：具体情境、额外付出、结果、他人反馈。
4. 边界：不是无限兜底，要学会暴露资源问题。
5. 沉淀：把一次性补位变成脚本/文档/流程。

**评分锚点**
- **5**：有真实补位案例，能沉淀为机制，边界清晰。
- **4**：愿意补位，有案例，沉淀意识弱。
- **3**：态度正面但无实例。
- **2**：只做分内事，强调「不是我的锅」。
- **1**：推诿或消极。

---

### B06 · 跨部门沟通 〔知识库·转译〕

**题目**（源：`KB-H` 题目 2 延伸）：你需要一个不属于你部门的同事配合，但对方一直说「排期满了」。你怎么推动？

**考察目的**：考察沟通影响力与推进能力，ToB 交付常见。

**参考答案要点**
1. 先理解：对方排期与优先级，确认自己的需求是否真的紧急。
2. 对齐价值：说明对共同目标/客户的影响，给出最小必要工作量。
3. 降低对方成本：提供清晰输入、示例、可复用的脚本或部分实现。
4. 升级机制：书面同步、找共同上级、调整排期，不越级告状。
5. 闭环：确认交付时间与验收方式，事后致谢与反馈。

**评分锚点**
- **5**：理解对方、价值对齐、降低对方成本、合理升级、闭环致谢，有案例。
- **4**：能沟通价值与排期，方法较常规。
- **3**：知道多沟通，缺具体手段。
- **2**：只会催或直接找领导。
- **1**：放弃或情绪化。

---

### B07 · 客户现场应急 〔知识库·转译〕

**题目**（源：`KB-A` 人力资源经理 Q5 的危机处理思路，转译为后端交付场景）：项目验收前一天，核心功能在客户现场不可用，负责人联系不上。你怎么办？

**考察目的**：考察应急判断、风险意识与担当，校招可接受不完美但要有序。

**参考答案要点**
1. 止损：确认影响面，保留现场，启用备用方案/回滚。
2. 上报：立即同步项目负责人与客户对接人，不隐瞒、不擅自承诺。
3. 定位：按日志/配置/环境差异快速排查，先恢复再根治。
4. 记录：时间线、操作、证据，便于复盘与验收说明。
5. 复盘：补充预案、演练、值班与联系机制。

**评分锚点**
- **5**：止损-上报-定位-记录-复盘有序，边界清晰，不擅自承诺。
- **4**：能先恢复并上报，记录一般。
- **3**：知道找人帮忙，缺止损意识。
- **2**：慌乱、隐瞒或擅自改生产数据。
- **1**：逃避或激化客户情绪。

## 四、HR 类（H01–H07｜初面官 H01，其余 HR 面官）

### H01 · 自我介绍与求职动机 〔知识库〕

**题目**（源：`KB-H` 题目 1）：请做自我介绍，并说明你为什么适合这个岗位、为什么选择恒信数字科技。

**考察目的**：综合考察表达逻辑、自我认知、岗位匹配度、求职诚意与行业认可度，快速筛掉海投与盲目求职。

**参考答案要点**
1. 结构：基本信息 → 与岗位相关的 2 个能力/经历 → 为什么这家公司 → 求职诉求。
2. 匹配：能把自己的项目/技能对应到岗位职责（后端开发、知识库、私有化交付）。
3. 公司认知：知道恒信做政企 AI 数字化、私有知识库、RAG/Agent、私有化部署，而非泛泛「AI 很火」。
4. 动机：看重平台与成长，表述稳定、不空喊。
5. 表达：2 分钟内，重点突出，不背模板。

**评分锚点**
- **5**：逻辑清晰、优势与岗位强相关、公司认知准确、动机真诚、稳定性好。
- **4**：介绍完整、匹配度较好、公司认知基本准确。
- **3**：介绍完整但泛泛，公司认知停留在「AI 公司」。
- **2**：照背模板，优势与岗位无关，说不清为什么投。
- **1**：表述混乱、盲目求职、明显海投。

---

### H02 · 职业规划与长期稳定 〔知识库〕

**题目**（源：`KB-H` 题目 3）：谈谈你的职业规划，以及你能为公司带来什么，未来 3 年打算如何发展？

**考察目的**：考察职场三观、稳定性、成长意愿与价值输出，筛选可长期培养、低流失率的人才。

**参考答案要点**
1. 短期（0–1 年）：补齐工程能力，独立承担模块，达到岗位合格线。
2. 中期（1–2 年）：深耕后端 + 知识库/私有化方向，成为模块骨干。
3. 长期（3 年）：技术专家或小组骨干，能带新人/沉淀组件。
4. 价值：稳定交付、可复用组件、排障与文档沉淀。
5. 稳定：择业看重平台与成长，不频繁跳槽；能说明为什么武汉/为什么这家公司。

**评分锚点**
- **5**：规划分层清晰、与岗位路径吻合、价值输出具体、稳定性有理有据。
- **4**：有清晰规划，价值输出较具体。
- **3**：有简单规划，目标不够落地。
- **2**：规划与岗位无关，或只看短期薪资。
- **1**：无规划、明显过渡、离职风险高。

---

### H03 · 薪资期望、地点与到岗 〔自研〕

**题目**：你的薪资期望是多少？能否接受武汉江夏办公？最早什么时候到岗？如果同时拿到其他 offer，你会怎么选？

**考察目的**：核实硬约束，避免入职前流失；同时观察沟通是否坦诚、是否做过功课。

**参考答案要点**
1. 薪资：给出合理区间，说明依据（城市/岗位/自身能力），不漫天要价也不自我贬低。
2. 地点：明确接受度；如有顾虑，提出可协商方案。
3. 到岗：给具体时间，与毕业/答辩安排一致。
4. 选择：说明决策标准（成长、技术方向、团队），不贬低其他公司。
5. 诚信：信息与简历一致。

**评分锚点**
- **5**：区间合理有依据，地点与到岗明确，决策标准成熟，信息一致。
- **4**：期望合理，约束清楚，选择理由一般。
- **3**：能给区间但依据不足，地点需考虑。
- **2**：期望明显脱离校招市场，或到岗时间含糊。
- **1**：无法接受地点/时间且无协商，或信息矛盾。

---

### H04 · 对恒信业务与岗位的理解 〔知识库〕

**题目**（源：`KB-J` 招聘简章 + `KB-C` 公司介绍）：你看过我们的资料后，怎么理解恒信的业务？你认为这个后端岗位每天在做什么？

**考察目的**：验证是否做过功课，以及岗位认知是否真实，降低入职落差。

**参考答案要点**
1. 业务：政企 AI 数字化、私有知识库、RAG、Agent 调度、工业视觉、低代码；客户在制造/政务/零售/教育。
2. 特点：私有化、内网、数据安全、项目制交付、定制化。
3. 岗位：写接口、做文档入库与检索、对接模型/向量库、权限与审计、部署与排障、写文档与测试。
4. 挑战：需求变更、现场问题、忙闲交替、既要交付又要沉淀。
5. 期待：能说出自己哪部分最感兴趣、哪部分需要学习。

**评分锚点**
- **5**：业务与岗位理解准确，能说出私有化/项目制的挑战，表达真实兴趣与学习计划。
- **4**：业务理解基本准确，岗位认知较完整。
- **3**：知道公司做 AI/知识库，岗位理解泛泛。
- **2**：明显没看资料，或把岗位理解成纯算法。
- **1**：认知严重错位。

---

### H05 · 学习方法与成长 〔自研〕

**题目**：最近半年你自学了什么？怎么学的？遇到过什么卡点？如果入职后两周要上手一个你没接触过的向量数据库，你会怎么学？

**考察目的**：考察学习能力与学习方法，校招最看重潜力的证据。

**参考答案要点**
1. 主题：具体技术/项目，不是「看书」。
2. 方法：官方文档 → 最小 demo → 源码/原理 → 应用到项目 → 输出笔记。
3. 卡点：能说出具体问题与解决路径，体现检索与求助能力。
4. 迁移：新技术的 2 周计划（跑通 demo、读文档、做对比、问同事、写总结）。
5. 证据：博客/GitHub/笔记/项目，能展示。

**评分锚点**
- **5**：有具体主题、方法成熟、卡点真实、迁移计划可执行，有产出证据。
- **4**：学习路径清晰，有产出，迁移计划一般。
- **3**：有学习意愿，方法较随意。
- **2**：只会说「看视频/背八股」。
- **1**：无自学经历，学习被动。

---

### H06 · 反问环节 〔自研〕

**题目**：你有什么想问我的？关于团队、业务、成长或面试流程都可以。

**考察目的**：考察关注点与思考深度；好问题往往比好答案更能说明动机。

**参考答案要点**
1. 高质量问题：团队当前最大的技术挑战、新人培养与导师制、知识库项目的典型交付周期、绩效如何评定。
2. 中质量问题：技术栈、加班情况、转正标准。
3. 低质量问题：薪资细节、能否远程、能不能不加班（可问，但要看时机与方式）。
4. 倾听：能基于回答继续追问，而非念清单。
5. 边界：不问其他候选人隐私、不问公司机密。

**评分锚点**
- **5**：问题有深度且与岗位相关，能追问，体现长期思考。
- **4**：问题合理，关注成长与业务。
- **3**：常规问题，无明显思考。
- **2**：只问薪资/加班，或说「没有问题」。
- **1**：问题冒犯或明显不关心岗位。

---

### H07 · 稳定性与离职风险 〔知识库·转译〕

**题目**（源：`KB-H` 题目 3 延伸）：如果你入职后发现工作内容与预期不符，或者团队氛围不适应，你会怎么处理？什么情况下你会考虑离开？

**考察目的**：评估离职风险与成熟度，避免短期流失；同时观察是否诚实。

**参考答案要点**
1. 先沟通：与导师/主管对齐预期，确认是信息差还是真实错配。
2. 先适应：给自己设定观察期，主动承担小任务建立信任。
3. 合理离开：长期无成长、价值观严重冲突、公司违约等，说明会提前沟通、做好交接。
4. 不情绪化：不因一次冲突或短期加班就离职。
5. 诚实：不掩饰「会看机会」，但能说明决策周期与条件。

**评分锚点**
- **5**：处理成熟、有观察期与沟通动作，离开条件理性，交接意识强。
- **4**：态度稳定，能沟通，离开条件较合理。
- **3**：回答正确但空泛。
- **2**：一有不适就走，或过度承诺「绝不离职」。
- **1**：明显短期过渡、频繁跳槽且无反思。

| 阶段 | 题号 | 题量 | 目的 |
|---|---|---|---|
| 初面（15 min） | H01、P01 | 2 | 动机、表达、项目真实性 |
| 技术面（45 min） | T01、T04、T05、T08、T11 + P03 或 P09 | 6 | 基础、RAG、检索、安全、性能、方案 |
| HR 面（30 min） | B01、B02、H02、H07 + H05 | 5 | 协作、抗压、规划、稳定、学习 |

> 技术面可按候选人背景替换 1–2 题（如无 RAG 经历，用 T06 替代 T05），但必须保持「基础 / 数据 / 接口 / 检索 / 部署」五个面全覆盖。

### 5.2 追问规则

- 每题最多追问 **2 轮**，每轮只问一个点。
- 追问优先级：实现细节 → 取舍理由 → 失败案例 → 量化结果。
- 候选人说「不知道」时，给一次提示后仍无进展即按当前档评分，不无限引导。
- 追问得到的增量信息必须写入评分依据，否则视为无效追问。

### 5.3 评分校准

- 技术面官与 HR 面官各自独立打分，不互相看分。
- 同一维度分差 ≥1.0 时，由评估官回看证据仲裁（见 `00-团队分工.md` 异常表）。
- 所有 5 分必须有「超出校招预期」的具体证据；所有 1 分必须能引用原话或明确未作答。

### 5.4 题库维护

- 每季度复盘一次：区分度低（人人 4 分）或过难（人人 2 分）的题替换。
- 知识库更新后，同步更新〔知识库〕/〔知识库·转译〕题目的参考答案与来源版本号。
- 新增题必须同时提供考察目的、答案要点、1–5 锚点与来源，否则不入库。
